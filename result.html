🔍 Key Observations from Item Analysis

  • Q9 (Confidence) scored highest (mean 4.30) — users generally felt confident while navigating the system.
  • Q5 (Integration) scored well (mean 4.05) — features feel cohesive and well-connected.
  • Q4 (Technical Support Needed) scored 3.05 — many respondents felt they might still need guidance, indicating room for better onboarding.
  • Q8 (Cumbersome) scored 3.00 — some users found the system burdensome, consistent with the SOS discoverability complaints.
  • Q10 (Learning Curve) scored 3.20 — a notable number of respondents needed time to understand the system before use.

Key Issues Identified

⚠️ Usability Issues Found During Testing

During the heuristic evaluation and usability testing sessions, the following key issues were identified and documented across different usability dimensions. Issues are tagged by severity based on how frequently they were raised.

  • 🆘
    SOS Button Discoverability High Severity Multiple respondents explicitly reported difficulty finding the SOS/emergency button. Comments included: "I can't find the SOS immediately," "the SOS should be found easily," and "I have a hard time finding it." This is a critical safety feature that must be prominently placed.
  • ⚠️
    No Cancel Confirmation Dialog High Severity One respondent noted: "when I cancel some actions, it immediately goes — I didn't see a warning." The lack of a confirmation prompt when cancelling rides or actions can lead to accidental loss of bookings.
  • 🔘
    Button Functionality Clarity Low Severity One respondent mentioned buttons need to be "sure it actually directs" and should be "easy to understand," suggesting that some interactive elements were unclear in their purpose or response.

Heuristic Evaluation Findings

🔍 Key Findings per Evaluator

Brian Al Tenorio — Visibility & User Control

The system generally provides visual feedback during the booking process; however, the current prototype lacks consistent status indicators on certain screens. The SOS/emergency button, a critical user control element, was found to be insufficiently visible and not placed in an immediately accessible location. Additionally, the absence of a cancellation confirmation dialog reduces the user's sense of control — the system should give users the freedom to undo or confirm actions before proceeding irreversibly. It is recommended to implement a persistent status bar, a prominently placed SOS button on the home/booking screens, and confirmation prompts for destructive actions such as cancelling a ride.

Shejay Barranda — UI Consistency & Design

The overall visual design is clean and follows a consistent blue color palette, which aligns well with the transportation/mobility theme. Rounded card components and icon usage are applied consistently across most screens. However, minor inconsistencies were observed in button sizing and padding across different screens, and some action labels used slightly different phrasing for similar functions. Font weight hierarchy was found to be effective for guiding user attention on the login and booking screens, but some secondary screens lack sufficient visual differentiation between interactive and non-interactive elements. Standardizing the component library and adopting a stricter style guide would resolve these inconsistencies.

Mary Rose Oriana — Error Prevention & Feedback

The prototype showed limited error-prevention mechanisms. Key gaps include: (1) the absence of a confirmation modal when the user attempts to cancel a booked ride; (2) no input validation feedback visible during the sign-up flow when fields are left incomplete; and (3) no pre-booking fare summary that allows users to review costs before confirming. These issues increase the likelihood of user errors and reduce trust in the system. The system should implement inline validation messages, cancellation confirmation dialogs, and a clear fare estimation screen prior to the final booking confirmation step.

Christine Joy Saor — Overall Usability & Efficiency

The core booking flow — from login to ride confirmation — is streamlined and requires relatively few steps, which supports task efficiency for experienced users. However, for new users, the lack of onboarding guidance or a walkthrough tutorial creates a learning barrier. The SOS button, while present in the prototype, is not positioned where users intuitively look during or after booking. Task completion during testing was generally successful for the main ride-booking scenario, but users spent more time than necessary on secondary actions such as locating safety features and navigating back from certain screens. Adding a brief onboarding flow, improving the SOS placement, and offering quick-access shortcuts for frequent actions would significantly improve efficiency.

Discussion

💬 Interpretation of Results

The overall mean SUS score of 63.25 places the Sakay Partido prototype within the "Acceptable" usability range (51–67.9) based on the standard SUS grading scale. While this indicates that the system is generally usable, it falls short of the "Good" (≥68) threshold, suggesting that meaningful improvements are still needed before the system is ready for broader deployment.

The high score on Q9 (mean 4.30 — "I felt very confident using the system") and Q5 (mean 4.05 — "The functions were well integrated") suggests that the overall design structure and feature set are intuitive and coherent. Respondents who are regular commuters and smartphone users found the core concept immediately relatable, which contributed to their confidence. The positive qualitative responses consistently praised the app's convenience and its potential to solve a real gap in local transportation — the absence of ride-hailing apps in the Partido area.

However, lower contributions from Q4 (Technical Support, contribution 1.95) and Q10 (Learning Curve, contribution 1.80) reveal that a notable portion of respondents felt the system required more effort to learn than expected. The wide standard deviation of 15.37 further indicates highly varied user experiences — some users rated the system as Excellent (85.0) while others gave Poor scores (37.5). This polarization likely stems from differences in prior familiarity with similar ride-hailing apps and the varying degree of difficulty in locating secondary features like the SOS button.

The most consistent issue raised — the SOS button discoverability — is a significant usability and safety concern. In a transportation context, emergency features must be immediately accessible without requiring users to search for them. Addressing this single issue may have the largest positive impact on the overall SUS score in a subsequent evaluation. Similarly, the lack of onboarding guidance for first-time users and the absence of a fare estimation screen are gaps that are well-documented best practices in ride-hailing application design.

In summary, the results suggest that Sakay Partido has a strong conceptual foundation and addresses a genuine local need, but the prototype requires targeted improvements in safety feature accessibility, error prevention, onboarding, and pricing transparency to achieve a "Good" or "Excellent" SUS rating in future evaluations.

Recommendations

✅ Recommendations for Improving the Prototype

Based on the SUS scores, heuristic evaluation findings of us(Sakay Patido Development Team), and qualitative feedback from respondents, the following improvements are recommended for the next version of the Sakay Partido prototype.

🆘

Relocate the SOS Button

Place the SOS/emergency button in a fixed, always-visible location (e.g., top right of the home page) so users can access it instantly.

📍

Make the Location Access Mandatory

Make the Location Access mandatory for the users to use the app for real-time tracking of drivers and their location.

🚫

Add Cancel Confirmation Dialog

Implement a confirmation modal whenever the user attempts to cancel a ride or perform a destructive action. This prevents accidental cancellations and improves user control.

🔘

Improve Button Labeling & Clarity

Ensure all buttons use clear, action-oriented labels. Avoid ambiguous icons without text. Provide hover/tap states to confirm user interaction.

Suggested Design Improvements

🎨 Design-Level Enhancements

Beyond functional fixes, the following design-level changes are suggested to elevate the user interface quality and align the prototype more closely with established mobile UX standards.

1

SOS Emergency Access

Adding SOS button in Homepage can solve the issue of having a hard time finding it. A prominently colored (red) SOS emergency button should remain accessible at all times during an active ride session. This directly addresses the most frequently told usability concern.

2

Consistent Component Library

Standardize button sizes, padding, and typography across all screens. Define a shared component set (primary button, secondary button, input fields, cards) so every screen feels cohesive. This addresses the inconsistency noted in the heuristic evaluation.

3

Mandatory Location Access

Making the Location Access mandatory for the users to use the app for real-time tracking of drivers and their location.

4

Error Handling Messages

Putting a clear and concise error handling messages to Cancel Booking and Saving a Place based on each members heuristic evaluation and the respondents usability evaluation.
